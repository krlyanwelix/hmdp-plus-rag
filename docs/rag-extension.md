# RAG 接入点设计（本期不实现）

赛事场景里，RAG 不是"加个客服"，它必须站在**业务漏斗的上游**：用户先问"我够不够格 / 这个组别适不适合我 / 赛道什么情况"，
再决定报不报。所以它的输出要能影响准入与选组，而不是答完就结束。

---

## 1. 三层知识源路由

一个问题进来，先判断该查哪一层，而不是一把梭全塞进向量库：

| 层 | 内容 | 手段 | 例子 |
|---|---|---|---|
| **L1 结构化** | 赛事、组别、余量、报名时间窗、报名费 | **不走向量检索，转工具调用**（查 DB / Redis） | "半马还有名额吗""报名什么时候截止" |
| **L2 非结构化** | 赛事规程、赛道说明、领物须知、强制装备 | 向量检索 + 关键词混检，按 `event_id` 过滤 | "越野组要带什么装备""关门时间多久" |
| **L3 个人上下文** | 实名档案、最好成绩、历史报名、禁赛状态 | **鉴权注入**，不进向量库 | "我能报 50 公里吗" |

路由判据：

- 命中时间/数字/是否存在这类**可枚举事实** → L1。这类问题绝不能交给模型自由发挥，
  余量答错会直接引发投诉。
- 命中规程、装备、路线描述 → L2。
- 命中"我""我的" → L3，且必须先过鉴权，否则会串号。

**为什么这一层路由最重要**：把 L1 交给向量库，是这类项目最常见的错误——
余量是每秒钟都在变的数字，向量库里存的是"某个时刻的文本"，答出来一定是过期值。

## 2. 知识源与切片

知识源只有一处：`tb_event.description`。切片策略按规程的结构来，不做定长切：

```
赛事规程
 ├─ 【报名资格】→ 一个 chunk（含年龄、成绩门槛、健康要求）
 ├─ 【赛道说明】→ 按距离分段（半马/欢乐跑/越野30/越野50 各一 chunk）
 ├─ 【领物须知】→ 一个 chunk
 ├─ 【强制装备】→ 一个 chunk
 └─ 【关门时间】→ 一个 chunk
```

每个 chunk 带元数据：`{event_id, group_id?, section, updated_at}`。
检索时 **`event_id` 作为硬过滤条件**（不能把 A 赛事的规程答给 B 赛事的用户）。
`updated_at` 用于回答时给出来源时间，并在规程更新后触发重嵌入。

---

## 3. 与三条链路的耦合点（这是这个项目的特色）

| 链路 | 耦合方式 |
|---|---|
| **鉴权** | L3 的答案必须经过准入校验，而不是模型"看"档案后自己下结论。问"我能报吗"，助手调 `checkQualification` 拿布尔值，再解释原因 |
| **缓存** | 赛事详情与组别余量已在多级缓存里，助手查 L1 时**复用同一套缓存**，不另建一份，避免"助手说有 3 个名额、页面显示已满" |
| **写路径** | 助手可以**发起报名**，但只能是"生成一个带 groupId 的跳转/预约动作"，真正的写入仍走 `POST /registration/{groupId}`，复用幂等与限流。绝不让模型直接调写接口 |

最后一条是关键约束：**LLM 只做理解与生成，写操作永远回到受控接口**。

## 4. 待建组件（下一期）

```
knowledge/
  ├─ EventDocLoader        读 description + 组别信息，产出 chunk 列表
  ├─ Chunker               按【】小节切分，保留 section 元数据
  ├─ Embedder              调嵌入模型（本地 ollama 或云 API）
  └─ VectorStore           向量库（Chroma / pgvector / Redis Search 三选一）

assistant/
  ├─ AssistantController   POST /assistant/chat  (SSE 流式)
  ├─ QueryRouter           L1/L2/L3 判定 + 改写
  ├─ Retriever             BM25 + 向量混检，RRF 融合，event_id 过滤
  ├─ ToolRegistry          getGroupQuota / getEventSchedule / checkQualification
  └─ AnswerComposer        带引用（section + updated_at）+ 拒答策略
```

`ToolRegistry` 里的工具全部是**只读**的，写操作不注册为工具。

---

## 5. 评测（没有它就没法说 RAG 做得好）

黄金集 30–50 条，覆盖三类问题，各自有明确判据：

| 类型 | 判据 |
|---|---|
| L1 事实类 | 与 DB/Redis 实际值一致（可自动校验） |
| L2 规程类 | 答案必须落在检索到的 chunk 内，且引用正确 |
| L3 个人类 | 未登录时拒答；跨账号不能串数据 |

指标：Recall@4、引用正确率、**拒答率**（问不到就该拒答，而不是编）。
其中"拒答"最容易被忽略，也最能体现工程质量。

---

## 6. 为什么本期不做

1. **依赖不可控**：嵌入模型与向量库都需要额外运行时，与"先跑通三条链路"的目标冲突。
2. **没有知识源就没有 RAG**：`description` 目前只有两条演示数据，做出来的检索评测没有意义。
3. **它必须是"增强"而不是"主线"**：如果主链路的超卖还没收敛，加一个会答错余量的助手，
   等于制造第二个故障源。

所以这一期只留接口边界与文档，代码等主链路稳定后再接。
